# MEd (MapEditor) revival

MEd v0.32 is an abandoned GTA III / Vice City / San Andreas map editor (Tony Wroblewski, 2005-2006). The original source is not available anywhere. This project recovers it by decompiling `MEdv032/MEd.exe` and rebuilding it as C++ with Qt. The readme grants an MIT-style license, so modifying and redistributing it is permitted.

Goal: keep the original C++ and Qt design, same class layout, buildable with a current toolchain. Start with GTA III, then Vice City and San Andreas.

## Reference decompile of the game itself: `gta3.exe` 1.0 (kept for future sessions)

The user asked to keep this decompile so it can be consulted later. It answers questions about how the GAME behaves (as opposed to how MEd behaves), for example how a building is linked to its LOD, and what the game does with the data MEd writes.

- Source binary: `GTA_3_1.0/gta3.exe` (2,383,872 bytes, build of 22 May 2002, Visual C++ with the RenderWare SDK; no RTTI and no symbols). A copy is imported as `re/gta3/gta3.exe`.
- Ghidra project: `re/gta3/project/` (project name `GTA3`, program `gta3.exe`), fully analysed. Open it with the same Ghidra as for MEd (see Tooling). Do not delete it; re-analysis takes several minutes.
- Names: `re/gta3/names.tsv` (`addr<TAB>name`), apply with `scripts/ApplyNames.java` the same way as for MEd but with project `GTA3` (`analyzeHeadless.bat re\gta3\project GTA3 -process gta3.exe -noanalysis -scriptPath re\scripts -postScript ApplyNames.java re\gta3\names.tsv`). Add names here as functions are understood.
- Exported text: `re/gta3/out/*.c` (decompiled functions that were read, with a header saying what they are). Regenerate with `scripts/XrefDecompile.java <outfile> <hex addr> ...`, which decompiles every function that references the given addresses (typically strings). `scripts/DumpAsm.java` also works on this project.
- Address conversion for strings in the file: virtual address = file offset + 0x400000 (for example the string at file offset 0x1f1594 is at 0x5f1594).
- Useful anchors (file offsets; add 0x400000): placement line format `'%d %s %f %f %f %f %f %f %f %f %f %f'` at 0x1f1594 (id, model, position, scale, rotation), IDE object formats `'%d %s %s %d %f %d'` and variants at 0x1f14c8-0x1f1560, `'Finished loading IPL'` at 0x1f17a4, island LOD names `IslandLODInd` etc. at 0x1ec1f0. The exe contains no "LOD" string other than those island names, so the game does not detect LOD models by reading the name prefix.
- Findings from this decompile are recorded below, under "gta3.exe findings".
- Exported text so far: `re/gta3/out/loader_xrefs.c` (placement loader, IPL file loaders, IDE loaders), `init_xrefs.c` (game init, LoadLevel, loading screen), `game_init.c` and `after99.c` (the loading sequence and the script-start stage). Names are in `re/gta3/names.tsv` (all `_maybe` names are inferred from the community's names for the same code, not proven).

## Check Map wizard (built 2026-10-11)

- Core: `src/core/mapcheck.h/.cpp` (`checkMap`, `gameParsePlacement`, `checkReportText`), tests `tests/test_mapcheck.cpp` (a small fake game folder, one fault at a time). It checks the map the way the game reads it: files listed in default.dat and gta3.dat exist; IPL lines parsed like `sscanf("%d %s %f x10")` after the game's line reader (255 characters, commas and control characters become spaces); lines with fewer than 12 values (skipped silently); section names must be lowercase `inst`/`end` for the game; missing `end`; unknown model ids (ignored silently); rotation `|w| > 1` (NaN matrix); height below -250 (user's experience: -200 safe, -2000 crashed); model DFF missing from `gta3.img` (error), TXD missing (warning, the game uses "generic"), no COL model (warning); total placements against the pool capacity 5500 + 1214 + 2802 = 9516 (`CPools::Initialise`, 0x004a1770; 8689 are used by the original map); LODs without a building, buildings without a LOD and duplicate placements, but ONLY those that the original game does not already have.
- The "original game" baseline is `src/core/mapcheck_baseline.inc`, GENERATED from the unmodified data with `validate_gta3 GTA_3_1.0 --baseline src/core/mapcheck_baseline.inc` (221 LODs without a building, 42 buildings without a LOD, 6 duplicates). Regenerate it only from a pristine GTA III 1.0 folder, never from an edited one. The untouched game must produce 0 errors and 0 warnings (the validator checks this and prints `MAP CHECK`).
- Verified on the real map: dropping one building to z = -2200 gives exactly five lines (the depth, the orphaned LOD, the orphaned building); moving or removing a building together with its LOD (Delete) is clean.
- Viewer: a real Win32 toolbar (Save All, Undo, Redo, Centre on Object, Delete, Check Map; Undo, Redo, Save, Centre and Delete are enabled only when they can do something, as in MEd) and F7 open the Check Map window: a list of problems, `Go to` (also double-click) centres the camera and selects the placement, `Check again`, `Copy report`, `Close`. It checks the map as it would be SAVED: files with unsaved edits are rebuilt like Save writes them. `med_viewer GTA_3_1.0 --shot x.bmp --check` prints the same report on the command line (add `--select`, `--move`, `--sink`, `--delete` to test edits).
- Gotcha fixed 2026-10-11: with an OpenGL window, `SwapBuffers` paints the whole client area, so child windows (the toolbar) are drawn over unless the main window has `WS_CLIPCHILDREN | WS_CLIPSIBLINGS`; the clear also uses a scissor so it stays inside the 3D view. To check what the user sees, launch the exe and screenshot the window with `Graphics.CopyFromScreen` on its rectangle (`build/window.png`).
- Layout: the 3D view is the window below the toolbar, so mouse y is converted with `app.toolbarH` before picking and un-projecting.
- Not done: IDE-level line checks (the game's IDE parser was not read), `path`/`zone`/`cull` section contents, x/y world bounds (not verified), and checks for Vice City and San Andreas.

## Viewer interface and performance (2026-10-11)

- Layout: toolbar on top; Scene panel on the left (the regions); the 3D view in the middle; Inspector on the right (300 px). The 3D view is the window area between the panels, so `glViewport` starts at `app.viewX` and mouse y is converted with `app.toolbarH`. Mouse x needs no change because the pick and un-project calls use absolute window coordinates.
- **Scene panel = MEd's Scene tab** (regions are the IPL files of gta3.dat: INDUST* = Portland, COMN*/COMS* = Staunton Island, LAND* = Shoreside Vale, `overview` and `props` = whole city). A check box per file; only checked files are drawn and can be picked (MEd: the visible flag at +0x19 of each file object in paintGL, picking and the display-list builder `0x00459d70`); Select all, Deselect all, "Only the selected row"; double-click centres on the region. `--only a,b` starts with only the files whose name contains a word. Not read in detail: the code of `CMapList` itself (its constructor `0x00457bd0` builds this tab; the "Load the current scene" button there is the scene loader `0x0040e720`).
- **Inspector** (after MEd's object properties: name, unique id, X/Y/Z, rotation, "move 10 points"): model name and id, IDE name, texture, draw distance, IPL file (and whether it is unsaved), rotation as quaternion and angle, scale, collision radius, LOD partners, editable X/Y/Z with Apply, X/Y/Z +-10 buttons, Centre, Delete (move below the map), Delete permanently. The window title also says what is selected, which is how to check selection without looking at the 3D view.
- **Speed**: models are vertex arrays drawn with one `glDrawElements` per material (`drawModel`, `buildGeometry`), not display lists built from `glVertex` calls. Measured on the user's GeForce GT 705 (NVIDIA driver 391.35), same view, 177 objects and 40,000 triangles: 51 ms per frame with display lists (20 fps) and about 16 ms with vertex arrays (60 fps), independent of window size, so the cost was the driver's handling of immediate-mode display lists. Region hiding helps on top of that in proportion to what it removes. `--benchmark n` (shot mode) prints ms per frame, the CPU split and the triangle count; `MED_NOVSYNC=1` turns vsync off for it.
- **Picking is NOT MEd's method any more** (deliberate, 2026-10-11): MEd uses OpenGL selection mode (3 x 3 pixel region, nearest hit); with vertex arrays that mode took 11 seconds per pick on this driver and froze the window. The viewer casts 9 rays (a 3 x 3 grid around the cursor) on the CPU against every candidate placement's triangles and takes the nearest hit (`pickInstance`, `src/viewer/raycast.h`, tested by `tests/test_raycast.cpp`): 3.7 ms, same object as MEd's method for the same click. Anything that must match MEd's behaviour for what is selected should be compared with `CMapView_pickAtMouse` (0x0045d320).
- **Small-object picking** (2026-10-11, user: "cannot click on smaller objects like the cones"): MEd's 3 x 3 pixel region is too tight for things a few pixels wide, and a click 4 px beside a cone hit the terrain behind it. `pickInstance` now collects the nearest hit per ray (`pickCollect`); if the nearest hit among the 3 x 3 rays is not a small placement (model bounding radius <= `kSmallPickRadius` = 4), it also casts 5 x 5 rays 3 pixels apart (up to 6 px from the cursor) and takes a small placement hit there, closest to the cursor first, unless it lies behind the nearest hit (t > 1.15 x nearest t). Verified on the traffic cones of props.IPL at ~25 units: clicks up to ~6 px away pick the cone, 8 px away picks the ground, clear ground still picks the ground. Test helper: `--pick-test <model>` clicks the centre of every drawn placement of the model (`--pos x y z --pitch 20` near 1238 -1030 16 for the cones). Not MEd behaviour (deliberate). CONFIRMED by the user (2026-10-11): "cones work fine" in the live editor.

## gta3.exe findings (game version 1.0, 2002 build)

- **Loading sequence** (`0x0048bed0` `CGame_Initialise`, called with `DATA\GTA3.DAT`): generic textures, particles, game variables, then `CFileLoader_LoadLevel` for `DATA\DEFAULT.DAT` and for `DATA\GTA3.DAT`, then paths, water, streaming (`MODELS\TXD.IMG`), animations, "Find big buildings" (`0x004a7680`, this is where LOD stand-ins are linked), traffic lights, scripts, "Position dynamic objects", vehicle paths, "Start script", "Load scene".
- **The loading bar is a step counter, not a size or time**: `0x0048d770` `LoadingScreen` adds 1.0 to a counter per call and draws `counter * 0.013698630` = counter / 73. 73 steps in GTA III 1.0: 3 before the files, 56 from the files (one per `TEXDICTION`, `COLFILE`, `MODELFILE`, `HIERFILE`, `IDE`, `IPL` and `MAPZONE` line in default.dat (9) and gta3.dat (47); `SPLASH`, `CDIMAGE`, `IMAGEPATH` do not tick), 14 after. Step numbers of the late messages: 60 Setup paths (82%), 64 Find big buildings (88%), 68 Load scripts (93%), 70 Position dynamic objects (96%), 71 Initialise vehicle paths (97%), **72 Start script (98.6%, shows as 99%)**, 73 Load scene (100%). The work of a step happens AFTER its message is drawn, so a crash at "99%" is a crash in the work that follows step 72: `0x00439400` (starts the main script), `0x00439040` (processes scripts: runs the first frame of main.scm), `0x0046d3f0` (a 6.8 KB per-frame update that looks like the camera), all before step 73. Adding or removing lines in gta3.dat changes the total of 73 and so the percentages.
- **What this means for a map-edit crash at 99%**: the LOD linking (step 64, 88%) and all file parsing (steps 4 to 59) had already finished without crashing, so the cause is not a malformed IDE/IPL/COL line and, very likely, not the LOD pairing. It is something that is first used when the main script runs its first frame and the camera is processed (player and camera placement, line-of-sight and ground checks against the world). Untested hypotheses to check in the code: a placement whose model has no collision loaded, a model missing from gta3.img, or an object near the player's start position. NOT verified.
- **`CFileLoader_LoadScene_ipl` (`0x00478370`)**: reads a text IPL line by line. A line starting with `#` (the FIRST character only) is a comment, empty lines are skipped, a section starts at a line whose first four characters are `inst`, `zone`, `cull`, `pick` or `path`, and `end` (first three characters) closes it. Section headers are matched by prefix, so for example `instance` would also open `inst`.
- **`CFileLoader_LoadObjectInstance` (`0x004786b0`)**: parses a line with `sscanf("%d %s %f %f %f %f %f %f %f %f %f %f")` and gives up silently unless it converted all 12 values (extra trailing fields are ignored, missing ones make it skip the line without any message). Then it looks up the model id in the model-info table (`0x0083d408`); an unknown id does nothing, again silently. A model whose info field at +0x24 is -1 becomes a `CBuilding` (100 bytes, or a 0x94-byte treadable building when it has path data), otherwise a `CDummyObject` (0x68 bytes); the quaternion is converted to a rotation angle with `acos(w)`. `0x004777c0` is a second, record-storing variant that uses a pool and prints `Size of this thing %d needs increasing` when the pool is full.
- **`CFileLoader_LoadLevel` (`0x00476290`)**: first character `#` = comment; `EXIT` stops; `IMAGEPATH`, `TEXDICTION`, `COLFILE <level> <file>`, `MODELFILE`, `HIERFILE`, `IDE`, `IPL`, `MAPZONE`, `SPLASH`, `CDIMAGE`. On the first `IPL` line it also loads `DATA\OBJECT.DAT`. Lines are matched by prefix, so a line like `IPL` must start in column 0.
- A line in an IPL that MEd or a hand edit writes with fewer than 12 values, or with a model id missing from every IDE, silently disappears in the game; MEd (see `IPL_loadTextFile`) fills missing numbers with 0 and does not warn. A "check map" step in the editor would catch these (not built yet).

## Recovered knowledge

- The game version is a byte at `this+8` of the IPL/IDE file objects: 1 = GTA III, 2 = Vice City, 3 = San Andreas.
- `0x00424b40` `IPL_loadTextFile`: reads `inst` lines. Field layouts: III = id, model, pos(3), scale(3), rot(4) (12 fields); VC = same with interior after the model (13 fields, or 12 without); SA = id, model, interior, pos(3), rot(4), lod (11 fields). Defaults: lod = 0xFFFF, interior = 0. Numbers are parsed as `double`.
- IPL text SAVE (confirmed, ported as `replaceIplInstSection` / `formatIplInstanceLine` in `src/core/ipl.cpp`): `IPL_saveFile` re-reads the original file, reopens it for writing, copies every line up to and including the `inst` line, writes one line per instance (instances flagged deleted, `short` at +0x64, are skipped), then copies everything from the first following `end` line to the end of the file. Everything outside the inst block (cull, zone, pick, comments before `inst`) is therefore preserved. Line format (`0x00423080` `IPL_formatInstanceLine`): fields joined with `", "`, numbers as `QString::number(x, 'g', 12)` (= `%.12g`), id, model name, then for Vice City and San Andreas the interior, then x y z, then for GTA III and Vice City the literal `1, 1, 1` scale, then the rotation x y z w, then for San Andreas the LOD index. The Visual C++ 7.1 runtime prints exponents with three digits (`-8.74228e-008`), as do the shipped files, and `fmt()` reproduces that. Verified: an unchanged re-save of all 13 shipped GTA III IPL files with placements is byte-identical to the originals (`GTA3.ZON` has no inst block and is never saved).
- Save behaviour of the viewer (Ctrl+S, `saveAll` in `src/viewer/main.cpp`): only IPL files with moved objects are written. Deliberate differences from MEd, all for safety: files go to `MEd_saved/` next to the game folder (or `--save-to dir`) unless `--in-place` is given; with `--in-place` the original is first copied to `<file>.med-backup` (MEd makes no backup); failures are reported (MEd opens the file for writing a second time and silently loses the edit when it is read-only, which is the "uncheck Read-Only" warning in its readme). Verified with `--select 560 250 --move 15 0 3 --save`: the saved INDUSTSE.IPL differs from the original in exactly one line, size, line count and CRLF are unchanged, and the game folder was not touched.
- `0x00423730` `IPL_saveFile`: writes text or binary IPL. Binary starts with `bnry`, then the instance count, then per instance 7 floats (pos xyz, rot xyzw) and 3 ints (id, interior, lod).
- In-memory instance object (doubles): pos x/y/z at +0x10/+0x18/+0x20, rotation at +0x40/+0x48/+0x50/+0x58, id at +4, interior at +0xc, lod (short) at +0x60, owning file index (short) at +0x74.
- IMG (class `CIMG`, game version byte at `this+8` = 1 or 2, directory entries kept in a list at `this+0xc`, image path QString at `this+0x10`):
  - `0x0041b1e0` `CIMG_loadDirectory`: reads 4 bytes; if the 4th is `'2'` ("VER2") it is a v2 archive (count u32, then 32-byte entries), otherwise v1 and the `.dir` file next to the `.img` is read. Entry = offset u32, size u32 (both in 2048-byte sectors), name 24 bytes. `0x0041abe0` adds an entry.
  - `0x0041a4e0` extract: `fseek(offset << 11)`, copies size x 0x800 bytes. `0x0041c790` append: opens "ab", pads to a sector boundary. `0x0041cce0` create: header is two ints plus 0x7f8 zero bytes (one sector). `0x0041b720` rebuild: writes `tempdir` and `tempimg`, then replaces the originals (this is what delete uses).
  - Not decoded yet: `0x0041a280`, `0x0041a9d0`, `0x0041ac70`, `0x0041aeb0` (probably read-entry-data and size/KB display helpers).
- IDE (`0x00418230` `IDE_loadFile`, writer `0x00417a40` `IDE_saveFile`): the file content is searched for section blocks and split into lines, then lines are split on commas. Three blocks are read in this order: `2dfx` (lines with more than 16 fields: id, x, y, z, then ints; MEd reads lights here even though the readme says 2DFX is not editable), `objs`, `tobj`.
  - GTA III / VC `objs`: needs more than 4 fields; reads id, model, txd, then ints (mesh count, draw distance, flags). `tobj`: more than 6 fields, adds time on and time off.
  - SA `objs`: 5 fields (id, model, txd, drawDist, flags) or 6 (one legacy column after txd, ignored). SA `tobj`: 7 or 8 fields (same rule). `ide.cpp` implements both.
  - MEd parses draw distance with `toInt`, so it keeps whole numbers only; the core library keeps `double`.
- Scene loader `0x0040e720` opens one IMG for GTA III (`Scene_openImgArchive` 0x0041f2c0 constructs a `CIMG` and loads its directory) and three for SA.
- Rendering in MEd (`CMapView`, fixed-function OpenGL, confirmed from the decompile):
  - `0x00458ea0` `CMapView_initializeGL`: clear colour black (0,0,0,0), clear depth 1.0, `glAlphaFunc(GL_GREATER, 0)`, blend `GL_SRC_ALPHA / GL_ONE_MINUS_SRC_ALPHA`, perspective hint nicest, `glPolygonMode(FRONT_AND_BACK, FILL)`, and a 20 ms-style `QTimer` that calls `pollKeyboard()`. Real lighting: one directional `GL_LIGHT0` at position (0, 0, 200, 0), ambient 0.4, diffuse and specular 0.7. It does not use baked vertex colours (they come out far too dark).
  - `0x0045bc40` `CMapView_paintGL`: `gluPerspective(fov 45, aspect, near 1.0, far 8000)`. The original computes the aspect with an integer division of width by height (an original bug); the viewer uses the proper ratio. Camera position is at `this+0x1c/0x20/0x24` (x, y, z), yaw at `+0x28`, pitch at `+0x2c`; eye is at (x, y - K, z) looking at (x, y, z) with up (0, 0, 1), pitch and yaw applied as `glRotatef` on the projection matrix. Each placement: `glPushMatrix`, `glTranslatef(pos)`, `glRotatef` from the quaternion, draw the model, `glPopMatrix`. Selected items additionally get a bounding box and sphere (`0x00404410`, `0x00404ff0`, `0x00404720`).
  - `0x00465850` `Quaternion_toNegatedAxisAngle`: axis = (x, y, z) / |(x, y, z)|, angle = -(2 * acos(w)) in degrees, so GTA III's stored quaternion is applied as its inverse. `src/viewer/main.cpp` does the same (`--conj 1`, the default).
  - Camera (`src/viewer/camera.h`, tested by `tests/test_camera.cpp`): state x, y, z, h, yaw, pitch (bookmark format `x:y:z:h:yaw:pitch:flag`). Projection `gluPerspective(45, aspect, 1, 8000)` then `glRotatef(pitch, 1,0,0)`, `glRotatef(yaw, 0,1,0)`. Modelview `gluLookAt(x, y-20, z, x, y, z, 0,0,1)` then `glTranslatef(0, 0, h-20)`, so the real eye is at (x, y-20, z+20-h). Light position is (0, -1, -0.5, 0), set while the modelview matrix still holds the previous frame's view; ambient 0.4, diffuse and specular 0.7. Defaults (`CMapView_ctor` 0x00459800): all camera values 0, mouse speed 20, shift multiplier 1.
  - `0x0045e530` `CMapView_pollKeyboard`, called by a `QTimer::start(1)` (1 ms), so movement is per tick: forward/back 0.5 (shift: multiplier x 3.0) along (sin yaw, cos yaw) and `h += sin(pitch) * step`; strafe 0.2 (shift: multiplier x 1.2) along yaw+90; up/down 0.5 (shift: multiplier x 4.0). Keys read with `GetKeyboardState`: W/S/A/D and cursor keys, Ctrl+forward/back or PgUp/PgDn move up and down, and R/F also move up and down (undocumented). Alt blocks camera movement because Alt+cursor moves the selected object. Other keys seen in that function: Esc, Space (centre on selection), Delete, Enter, F11 and others, not ported yet.
  - `0x00462130` `CMapView_mouseMoveEvent`: left button rotates (`yaw += mouseSpeed * 0.01 * dx`, `pitch += ... dy`, wrap above 360 to 0 and below 0 to 359); Ctrl + left button moves with a fixed step per event (forward multiplier x 2.8, sideways x 1.8, height 0.8 along pitch, direction of motion only).
  - MEd's own help text (stored as HTML at file offset 0x2d9400 in MEd.exe) is the authority for controls: left button rotate; Ctrl+left move; W/S/A/D or cursor keys move; wheel or Numpad +/- forward and back; Ctrl+cursor, Ctrl+W/S, PgUp/PgDn up and down; Shift faster; Space centre on selection; Esc exit full screen or cancel selection; Del delete; Alt+cursor keys or Alt+left button move the selected object; Alt+PgUp/PgDn move it up and down; double-click selects, Shift+double-click multi-selects, right-click object menu, Shift+right-click multi-object menu; double-click, Enter, Esc or F11 leave full screen.
  - Selection and moving (ported, `src/viewer/main.cpp`; the key/step logic is in `camera.h` and tested):
    - `0x0045d320` `CMapView_pickAtMouse`: classic OpenGL selection mode. 6000-entry select buffer, 3 x 3 pixel pick region at (x, viewportHeight - y), same projection and view as paintGL, every visible placement drawn with its real model display list under `glLoadName(its serial)`. The nearest hit wins (minimum depth normalised to 0..1, negative values get +2^32 first). The viewer picks among the placements it drew that frame, which matches MEd because MEd draws everything.
    - `0x0045e2a0` `CMapView_mouseDoubleClickEvent`: leaves full screen first, does nothing if editing is off. No hit clears the selection. Without Shift, hitting the first selected item deselects all, otherwise the hit replaces the selection. With Shift the hit is added or removed. Selected ids are kept in a list at `this+0x68`; `this+0x90` holds the current id (-1 for none).
    - Selected objects are drawn with `0x00404410` `DrawSelectionBoundsAndAxes`: at the bounding-sphere centre of the COL model, green Y, red X and blue Z axis lines of +-200 with a 2-unit tick every 10 units, a circle of the bounding radius in the XY plane (360 vertices as `GL_LINES`, so it is dashed), then a red wireframe box of the COL bounds (`0x00404280` `DrawWireBox`). The data it reads is exactly the COL model bounds: box at +0x2c..+0x40, centre at +0x44..+0x4c, radius at +0x50. Placements are drawn without scale in MEd (GTA III scales are all 1).
    - Alt + left button drag (`0x00459270` `CMapView_unprojectMouseToPlane`): `gluUnProject` at window depth 0 and 1, intersected with the horizontal plane at `z - h` (this is why bookmarks keep `z - h` near ground level). Each mouse move adds the difference between the new and previous plane point to every selected object's x and y. Original bug fixed: MEd adds the near point twice to x and y.
    - Alt + cursor/WASD: 0.1 per tick (shift multiplier when Shift is held) along (sin yaw, cos yaw), strafe along yaw + 90; Alt+Ctrl+cursor or Alt+PgUp/PgDn move up and down (`0x0045e530`). MEd calls `0x004116a0` (undo snapshot, flag at `this+0xb0`) before the first change; undo is not ported yet.
    - Esc cancels the selection (in MEd it also leaves full screen); the viewer no longer quits on Esc.
  - Undo and redo (ported: `src/core/history.h`, tested by `tests/test_history.cpp`, wired in the viewer): MEd keeps whole-document snapshots on two lists, undo at `this+0x30` and redo at `this+0x34` of the document object. `0x004116a0` `Document_pushUndoSnapshot` deep-copies every IDE file and every IPL file (all instances plus their flags), appends it to the undo list and, when the list is longer than 5, deletes the oldest. `0x00413350` `Document_undo`: returns false when the undo list is empty, otherwise pushes the current state on the redo list (`0x00411e50`), restores the last undo snapshot and pops it. `0x00412600` `Document_redo` is the mirror image. The toolbar handlers `0x0044f8e0` (undo) and `0x0044f930` (redo) run the restore, refresh the trees and views, then call `0x0045c580` `CMapView_cancelSelection`, so undo and redo cancel the selection. MEd has toolbar buttons only ("Undo Changes", "Redo last undo"), no keyboard shortcuts, and enables them via `setUndo(bool)` / `setRedo(bool)`.
  - What counts as one undo step: the camera view takes a snapshot before the first change (`this+0xb0` flag, set in `pollKeyboard`, `mouseMoveEvent` and `CMapView_centreOnPoint`) and clears the flag again only when the selection changes or is cancelled (`CMapView_selectItem_maybe`, `CMapView_cancelSelection`). So moving one selection around any number of times is a single undo step; `centreOnPoint` (`0x00459130`, the Space key: sets camera x = object x, y = object y - 20, z = object z + 20, yaw 0, pitch 45, h 0) also snapshots.
  - Deliberate changes to undo (all in `history.h`): the limit is 20 actions, not 5 (the user asked for 20; MEd's readme says "up to 5"); a new edit clears the redo list (MEd leaves stale redo entries, so a Redo after a new edit jumped the document to an unrelated older state); the viewer binds Ctrl+Z, Ctrl+Y and Ctrl+Shift+Z because it has no toolbar yet.
  - Delete (ported: `removeIplInstance` in `src/core/ipl.cpp`, `deleteSelected` in the viewer, bound to the Del key as in MEd's `pollKeyboard`): `0x0045d0a0` `CMapView_deleteSelected` does nothing when nothing is selected; otherwise it always takes an undo snapshot first (`Document_pushUndoSnapshot`, not guarded by the once-per-selection flag, so a move followed by a delete is two undo steps), then for each selected serial id finds the IPL file that holds it (`0x00423490` `IPL_findInstanceBySerial`, which returns the last match) and calls `0x00424490` `IPL_removeInstance`, then clears the selection and rebuilds the display lists. There is no confirmation dialog for objects. `IPL_removeInstance` really erases the instance (it is not just flagged) and repairs the LOD links of the other instances in that file: a link to the removed instance becomes 0xFFFF and links above it move down by one (`short` at instance +0x60). The viewer keeps the placement-to-file mapping in the undo state too, because deleting changes the list.
  - Delete in the viewer is NOT MEd's behaviour, by the user's decision (2026-10-11): MEd's real removal crashes the game, and the user's own experience from earlier GTA III map making is that a building and its LOD stand-in reference each other, and that setting the height of both to -200 is safe while -2000 crashed the game. So: Del and the menu entry "Delete Object (move below the map)" call `sinkSelected` (z = -200, `kSunkZ` in `src/viewer/menu.h`, for the object and its LOD partner, one undo step); Shift+Del and "Delete Object permanently (remove from file)" call `deleteSelected` (MEd's real removal, but it removes the LOD partner too; UNVERIFIED in the game, ask the user to test it). Right-click opens the menu (`src/viewer/menu.h`, tested): single-object menu with Centre on Object (live, `centreOnObject`), Properties, Extract Object, Duplicate Object, Replace Object, Copy (greyed, not ported) and the two deletes; Shift+right-click or several selected objects gives MEd's "Selected Items" menu (Copy greyed, the two deletes). Space centres on the selected object. MEd's labels come from its string table (slots `extractObject`, `duplicateObject`, `centreObject`, `replaceObject`, `deleteObject(s)`, `copyObject(s)`, `pasteObject`, `newObject`); the order of the entries in MEd's own menu was not read.
  - LOD pairing (`findLodPartners`, `src/core/ipl.cpp`; validated on GTA III 1.0): evidence from the data, not yet from the game code. A LOD placement is named "LOD" + X and its building "<3 letters>" + X (`LODpitaland` / `hospitaland`), at the same position (660 of 759 pairs at distance 0, 737 within 1 unit, all but 12 within 5, 755 in the same IPL file). In the IDE, LOD models have draw distances of 600 to 3000 and normal models are almost all below 300; 713 name tails are shared by exactly one LOD model and one normal model. Only 745 of the 7721 normal placements have a LOD partner, so about 90 percent of objects have none. `gta3.exe` 1.0 contains no "LOD" string except island names, so the game does not detect LODs by reading the prefix; how it really links them (probably by IDE draw distance plus the shared name tail, then by position) is unconfirmed. Confirming it means decompiling `GTA_3_1.0/gta3.exe` (not done).
  - Delete caveat from MEd's own readme: "Re-enabled Deletion (Still causes Random Crashes in game!)" and "Only delete objects if you know what you are doing, ensuring they are not used or referenced by anything else in the game". The cause of those crashes is not known (not investigated); it is not the file writing, which is verified. Test deleted maps in the game before trusting them.
  - Mouse wheel (`0x00459540` `CMapView_wheelEvent`, ported as `cameraWheel`): one step per event, forward for delta > 0: 0.7 for x, y and h; with Shift 3.7 for x and y and 10.0 for h (`h` changes by sin(pitch) times the step).
  - Not ported yet: Space (centre on selection; the camera part is `CMapView_centreOnPoint`), copy/paste, "new item", replace item, the Numpad +/- keys (the help text lists them with the wheel; the keyboard code seen so far reads them as forward/back like W/S), binary IPL saving in the viewer (San Andreas), IDE saving (`IDE_saveFile` 0x00417a40 is located but its output format is not yet compared with the core writer), full screen, the context menus, the properties panel
  - Also not ported: the display list `CMapView` draws first (`this+0x44`, unidentified) and the shift multiplier / mouse speed UI (the viewer uses MEd's defaults 1 and 20). The viewer currently skips placements beyond their IDE draw distance and `lod*` models; MEd draws all placements of the visible files.
  - Not yet read: `0x00459d70` (7.9 KB, builds display lists), the model draw functions around `0x004035a0`, and mouse and keyboard handling (`pollKeyboard`).
- `src/viewer/main.cpp` is a Win32 + OpenGL 3D viewer on `med_core` (target `med_viewer`, no extra dependencies, no Qt). ## Working rules

- Fidelity first: the user wants the result as close to MEd v0.32 as possible. Match MEd's behaviour (render state, camera, controls, file handling) using the decompile, not generic choices. Where the original has a bug, fix it and record it here under "Original bugs fixed" so the difference is deliberate. Do not drift into your own design.
- Original bugs fixed so far: (1) aspect ratio computed with integer division of window width by height (`CMapView_paintGL`); the viewer uses the true ratio.
  (3) saving a GTA III or Vice City IPL wrote the literal scale `1, 1, 1` and so discarded real scales (`IPL_formatInstanceLine`); the core writes the real scale (identical output for all shipped data). (4) a save to a read-only file was silently lost; it is reported as an error now. (5) Replace Object took its undo snapshot before the chooser opened, so a cancelled replace still left an undo step (`CMapView_replaceObject` 0x00460aa0); the viewer snapshots only when something changes.
  (2) Alt+drag moving added the near-plane point twice to x and y (`CMapView_unprojectMouseToPlane`); the viewer uses the true ray/plane intersection (`rayPlaneIntersection`, tested).
- Original quirks kept on purpose (change only if the user asks): angle wrap in the mouse rotate (below 0 jumps to 359, not 359.x); the light direction is applied with the previous frame's modelview matrix; strafing with Ctrl+mouse changes `h` by the pitch.

- Never modify files in `MEdv032/`. Experiment on copies.
- Recovered code is not source-identical. Verify behavior against the real file formats and against the running original.
- GTA III 1.0 is extracted at `GTA_3_1.0/` in this project (from `GTA_3_1.0.7z`). Treat it as read-only: never write inside it. For any write test, copy the files to a temp folder first. The readme warns that deleting objects can crash the game.
- Validate against the real game with `g++ -std=c++17 -o build/validate_gta3.exe tools/validate_gta3.cpp src/core/*.cpp` then `build/validate_gta3.exe GTA_3_1.0` (read-only).
- Rewrite decompiler output into clean, readable Qt/C++ by hand. Qt-heavy parts (moc glue, widgets) are messy and are best rewritten rather than transcribed.
- Target modern Qt 6 with CMake. Qt 4.1.1 will not build today.
- Order of recovery: IMG, IDE, IPL parsers first (self-contained), then DFF/TXD/COL, then the OpenGL map view, then the Qt UI.
